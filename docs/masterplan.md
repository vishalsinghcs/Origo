# Origo Masterplan: Comprehensive End-to-End Implementation Guide

This document is the definitive, step-by-step architectural blueprint and execution plan for building and deploying **Origo**, the Enterprise AI Security Gateway. It details the precise role of every component, the exact methodologies for data synthesis and model training, and the complete infrastructure rollout using Docker and AWS.

---

## Architecture Overview

Origo operates as a multi-layered security proxy sitting between enterprise users and external LLM APIs (like OpenAI or Anthropic). 

1. **Layer 0 (Heuristics):** High-speed regex and entropy scanning for obvious threats (credit cards, standard API keys).
2. **Layer 1 (Semantic Router):** A fine-tuned Qwen2.5-3B model that classifies prompts as `SAFE`, `SUSPICIOUS`, or `UNSAFE` in milliseconds.
3. **Layer 2 (Specialist Rewriter):** A fine-tuned Qwen3-8B model that deeply analyzes `SUSPICIOUS` prompts, extracts sensitive entities, and rewrites the prompt to safely redact data or neutralize injection attacks.
4. **Layer 3 (Policy Engine):** A deterministic rule engine that applies company-specific thresholds (e.g., "Block all PII regardless of context") to Layer 2's output.

## Phase 1: Synthetic Data Generation & Engineering

Since real enterprise security data is highly sensitive and scarce, Origo relies on massive, high-quality synthetic datasets generated by advanced "teacher" LLMs.

### 1.1 Generation Scripts
- **`generate_layer1.py`**: Generates data to train the Layer 1 Router. Uses true parallelism via `asyncio` across multiple API keys to generate thousands of `SAFE`, `SUSPICIOUS`, and `UNSAFE` samples. Outputs chunked `.jsonl` files to `datasets/raw/layer1`.
- **`generate_layer2.py`**: Generates complex reasoning data for the Layer 2 Rewriter. It creates intricate scenarios involving PII exposure, credential leakage, and prompt injections. It strictly formats outputs with original prompts, detected entities, reasoning, action (`REDACT`, `REWRITE`, `BLOCK`), and the sanitized prompt. Outputs to `datasets/raw/layer2`.

### 1.2 Prompting & Prompts Directory
- **`prompts/layer1_prompts.py`**: Contains the strict system prompts instructing the teacher model on exactly how to simulate benign vs. malicious user queries for Layer 1.
- **`prompts/layer2_prompts.py`**: Contains the complex instructions for Layer 2 data generation, enforcing strict JSON schemas and edge-case handling (e.g., `false_positive_safe`).

### 1.3 Data Pipeline & Processing
- **`filters/quality_filter.py`**: Reads the raw `.jsonl` chunks. Uses N-Gram hashing and semantic deduplication to ensure the dataset has no overlapping or identical prompts. Drops malformed JSONs or low-quality generations. Saves to `datasets/filtered/`.
- **`convert_layer1.py` & `convert_layer2.py`**: Transforms the filtered, raw JSON data into standard `ChatML` or HuggingFace conversational formats required for fine-tuning. Saves to `datasets/processed/`.

## Phase 2: Model Fine-Tuning (AWS Setup)

To train our models (3B and 8B), we require significant GPU VRAM. This phase will be executed entirely on AWS.

### 2.1 AWS Infrastructure Provisioning
1. **Instance Selection**: Spin up an Amazon EC2 `g5.2xlarge` (1x A10G 24GB GPU) for Layer 1 training, and a `g5.12xlarge` (4x A10G) or `p4d` instance for Layer 2 training.
2. **Environment**: Use the AWS Deep Learning AMI (Ubuntu).
3. **Storage**: Attach a 200GB EBS NVMe drive to store datasets and model checkpoints.

### 2.2 Fine-Tuning Workflow
1. **Unsloth Integration**: We will utilize `Unsloth` to optimize the Qwen2.5 base models, allowing for 2x faster training and significantly reduced VRAM usage via 4-bit quantization (QLoRA).
2. **Layer 1 (Router)**: 
   - Base Model: `Qwen/Qwen2.5-3B-Instruct`
   - Task: Sequence Classification / SFT.
   - Run the processed Layer 1 ChatML dataset through the HuggingFace `SFTTrainer`.
3. **Layer 2 (Rewriter)**:
   - Base Model: `Qwen/Qwen3-8B`.
   - Task: Complex reasoning and entity extraction.
   - Train using the Layer 2 dataset with a focus on strict JSON output adherence.
4. **Adapter Merging**: Once training converges, export the LoRA weights and merge them back into the base models to create standalone `.gguf` or `Safetensors` artifacts.

## Phase 3: Core Gateway Backend (FastAPI)

The backend orchestrates the models and provides the API interface for the enterprise.

### 3.1 Inference Engine (`vLLM`)
- We will host the merged Qwen models using `vLLM` to achieve massive concurrency and continuous batching.
- The vLLM server will run locally alongside the backend or as a separate container, exposing an OpenAI-compatible endpoint.

### 3.2 FastAPI Application Structure
- **`api/main.py`**: The entry point exposing the `POST /v1/chat/completions` proxy endpoint.
- **`api/security/layer0.py`**: Standard regex/entropy checks.
- **`api/security/layer1.py`**: Calls the vLLM 3B model. If `SAFE`, immediately passes the prompt to the external API (OpenAI/Anthropic).
- **`api/security/layer2.py`**: If Layer 1 says `SUSPICIOUS`, this calls the vLLM 8B model to perform redactions and rewrites.
- **`api/security/layer3.py`**: Compares Layer 2's JSON output against the enterprise database rules (e.g., checking if the specific user has clearance to send PII).

---

## Phase 4: Admin Dashboard & Audit Logging

A React frontend for security officers to monitor AI traffic and adjust rules.

### 4.1 PostgreSQL Database Setup
- **Schema**: Tables for `audit_logs` (storing timestamp, user ID, original prompt, rewritten prompt, triggered threats, latency), `policies` (dynamic rules), and `users` (RBAC).
- **ORM**: Use `SQLAlchemy` or `Prisma` in the backend to interact with the database.

### 4.2 React (Vite) Frontend
- **Stack**: TypeScript, React, Vite, and TailwindCSS for a highly polished, modern aesthetic.
- **Views**:
  - **Dashboard**: High-level charts (Threats Blocked over time, Latency averages) using Recharts/Chart.js.
  - **Audit Trail**: A real-time, searchable data grid showing exactly what prompts were intercepted, the entities detected by Layer 2, and the resulting action.
  - **Policy Configuration**: Toggles for specific threat types (e.g., strictly block all source code, but rewrite credit cards).

---

## Phase 5: Containerization & Production Deployment

The entire stack will be containerized and deployed to AWS for high availability.

### 5.1 Dockerization
We will write specific `Dockerfiles` for each service:
1. **Frontend**: Nginx serving the Vite static build.
2. **Backend**: Python 3.11 image running FastAPI via Uvicorn.
3. **Inference**: Official `vLLM` Docker image loading our fine-tuned weights.

### 5.2 Orchestration (`docker-compose.yml`)
- A master `docker-compose.yml` will define the networking between the Frontend, the FastAPI Backend, the PostgreSQL database, and the vLLM GPU containers.
- This allows a developer to spin up the entire enterprise gateway locally with a single `docker compose up` command.

### 5.3 AWS Production Rollout
1. **Database**: Provision an Amazon RDS for PostgreSQL instance for managed, durable audit logs.
2. **Compute**: Deploy the Backend and Frontend containers using AWS ECS (Elastic Container Service) on Fargate.
3. **GPU Compute**: Deploy the vLLM inference containers on an ECS cluster backed by EC2 GPU instances (`g5.xlarge`).
4. **Networking**: Use AWS ALB (Application Load Balancer) to securely route enterprise traffic to the FastAPI endpoints, utilizing HTTPS/SSL certificates from AWS ACM.
